# 网约车（打车）系统 —— 数据库课程设计实验报告

---

## 摘要

本系统实现了一个简化的城市网约车平台，覆盖「乘客下单 → 平台派单 → 司机接单 → 行程执行 → 订单状态追踪 → 自动计价」的完整业务闭环。

技术方案为 **MySQL 8.4 + FastAPI + 手写 SQL（不使用 ORM）+ Jinja2 服务端渲染**。选择手写 SQL 而非 ORM，是因为本课程设计的核心是数据库设计与 SQL 能力，ORM 会把建表、连接、事务这些真正需要考察的内容隐藏在框架之后。

数据库共设计 **16 张表、30 个索引、6 个视图、1 个存储函数、6 个存储过程、1 个触发器**。系统在 **900 条订单**的演示数据上完整跑通了业务流程，并通过多线程并发测试验证了抢单场景的正确性。

设计过程中实测发现并修复了**六个真实缺陷**：并发接单的死锁、触发器与批量导入相互作用导致的数据重复累加、`GET DIAGNOSTICS` 的作用域陷阱、存储生成列对外键的隐含限制、"设置了随机种子却不可复现"的数据生成问题，以及触发器增量公式的舍入误差累积。这些问题的发现与解决过程构成了本报告第七章。

## 一、需求分析

### 1.1 业务背景

网约车平台的核心是把「乘客的出行需求」与「司机的运力供给」在时空上匹配起来。与普通电商系统相比，它有三个显著的数据库设计难点：

1. **强时序性**：订单有明确的状态流转，且每个状态节点的时间都必须可追溯；
2. **强并发性**：同一订单可能同时推送给多名司机，抢单是天然的并发场景；
3. **价格需可追溯**：平台会调价，但历史订单的金额必须永远不变。

### 1.2 功能需求

需求文档给出了 7 项核心需求与 7 项选做需求。本系统**全部实现 7 项核心需求**，并完成 **4 项选做需求**（评价与服务分、区域供需统计、证照到期提醒、车辆轨迹回放）。

| 编号 | 核心需求 | 本系统的实现方式 |
| --- | --- | --- |
| C1 | 乘客下单（可复用常用地址） | 存储过程 `sp_create_order`；`common_address` 表 |
| C2 | 平台派单与司机接单/拒单 | 存储过程 `sp_dispatch_order`；`order_dispatch` 表 |
| C3 | 司机行程执行 | 条件更新推进状态 + `sp_complete_order` |
| C4 | 订单状态实时追踪 | 六状态机 + 六个时间戳列 + 状态日志表 |
| C5 | 订单自动计价 | 存储函数 `fn_calc_fare` + 订单价格快照列 |
| C6 | 司机与车辆管理 | `driver`/`vehicle` 表 + 三层资格防护 |
| C7 | 账号与角色管理 | `account` 泛化模型 + 服务端会话表 |

### 1.3 需求中的三个设计难点

**(1) 需求 C4 要求「记录各状态节点的时间」**

这句话隐含了一个选择：是在订单表上放一个 `status` 字段加几个时间列，还是拆一张独立的「状态变更历史表」？

**(2) 需求 C6 要求「只有车辆处于可运营状态时才能接单」**

这是一条**跨表约束**，涉及司机在线状态、司机审核状态、账号状态、车辆运营状态四个字段，分属三张表。而 MySQL 的 `CHECK` 约束**不能跨表**。

**(3) 需求 C2 要求「平台派单」且「司机可以拒单」**

拒单这个动作**不改变订单状态**（订单仍是「待接单」，只是不派给这个人）。那么它记录在哪里？如果只在订单表上加一个 `driver_id`，拒单将无处安放。

这三个难点的解决方案见第二章。

## 二、数据库设计

### 2.1 概念结构设计

系统的核心实体与联系如下（完整 ER 图见 `docs/ER图.md`）：

```

                        └────┬─────┘
                             │ 1:N
                        ┌────▼─────┐

       │  1:1           └──────────┘  1:1           │ 1:1
  ┌────▼─────┐                              ┌───────▼──┐        ┌────────┐
  │passenger │                              │  driver  │        │ admin  │
  └────┬─────┘                              └───┬──┬───┘        └────────┘
       │ 1:N                                    │  │ 1:N
  ┌────▼──────────┐                         ┌───▼──▼───┐
  │common_address │                         │ vehicle  │
  └───────────────┘                         └───┬──────┘
                                                │ 1:N
       │ 1:N                                    │
  ┌────▼────────────────────────────────────────▼────┐
  │                    ride_order                    │ 订单（核心）
  └──┬────────────┬──────────────┬───────────────┬───┘
     │ 1:N        │ 1:N          │ 1:N           │ 1:1
 ┌───▼────┐  ┌────▼─────┐  ┌─────▼─────┐  ┌──────▼──────┐
 │status_ │  │  order_  │  │order_track│  │order_review │
 │  log   │  │ dispatch │  │           │  │             │
 └────────┘  └──────────┘  └───────────┘  └─────────────┘
   状态日志     派单记录       轨迹点         评价
```

**唯一的 M:N 联系**是「订单」与「司机」在**派单阶段**的关系：一个订单可派给多名司机，
一名司机可收到多个订单的邀请。用 `order_dispatch` 中间表拆解，并附带邀请状态、轮次、
应答时间等**关系属性**。若把这一关系直接塞进订单表，则拒单动作无处安放（见 1.3 的难点 3）。

### 2.2 逻辑结构设计

#### 2.2.1 账号与角色的泛化/特化模型

三种角色（管理员、司机、乘客）共享「用户名 + 密码 + 角色」这套登录凭证，
但各自的业务属性完全不同（乘客有常驻区域，司机有驾驶证与服务分）。

**采用泛化/特化设计**：统一的 `account` 表存登录凭证，三张档案表（`admin`/`passenger`/`driver`）
各存特有属性，通过**唯一的 `account_id` 外键**与 `account` 形成 1:1 关系。

优点：
- 登录逻辑只需查一张表，不用在三张表之间尝试；
- 用户名唯一性只需在 `account` 上建一个唯一索引，天然避免「司机和乘客用了同一个用户名」；
- 各角色属性可独立扩展，互不影响。

#### 2.2.2 核心表结构

完整字段字典见 `docs/数据库设计说明.md`，此处列出核心表 `ride_order` 的设计要点：

```sql
CREATE TABLE `ride_order` (
    `order_id`      BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    `order_no`      VARCHAR(32)     NOT NULL COMMENT '业务订单号',
    `passenger_id`  BIGINT UNSIGNED NOT NULL,
    `driver_id`     BIGINT UNSIGNED     NULL COMMENT '未接单为 NULL',
    `vehicle_id`    BIGINT UNSIGNED     NULL,
    `car_type_id`   TINYINT UNSIGNED NOT NULL,
    `origin_address` VARCHAR(200)   NOT NULL,
    `origin_region`  VARCHAR(50)    NOT NULL COMMENT '派单与区域统计的核心字段',
    `dest_address`   VARCHAR(200)   NOT NULL,
    `status` ENUM('pending','accepted','arrived','in_progress','completed','cancelled')
             NOT NULL DEFAULT 'pending',

    -- 六个状态节点时间（服务 UI 时间线渲染）
    `created_at`   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `accepted_at`  DATETIME NULL,
    `arrived_at`   DATETIME NULL,
    `started_at`   DATETIME NULL,
    `completed_at` DATETIME NULL,
    `cancelled_at` DATETIME NULL,

    -- 计价规则溯源 + 价格快照（下单时刻固化）
    `pricing_rule_id`       BIGINT UNSIGNED NULL,
    `rule_version`          INT UNSIGNED    NULL,
    `snap_base_price`       DECIMAL(10,2)   NULL,
    `snap_base_distance_km` DECIMAL(6,2)    NULL,
    `snap_per_km_price`     DECIMAL(10,2)   NULL,
    `snap_per_min_price`    DECIMAL(10,2)   NULL,
    `snap_min_price`        DECIMAL(10,2)   NULL,

    `distance_km`  DECIMAL(8,3) NULL,
    `duration_min` DECIMAL(8,2) NULL,
    `fare_amount`  DECIMAL(10,2) NULL,

    -- 生成列：仅「进行中」订单取值，配合唯一索引强制一司一单
    `active_driver_id` BIGINT UNSIGNED
        GENERATED ALWAYS AS (
            CASE WHEN `status` IN ('accepted','arrived','in_progress')
                 THEN `driver_id` ELSE NULL END
        ) STORED,

    PRIMARY KEY (`order_id`),
    UNIQUE KEY `uk_order_no` (`order_no`),
    UNIQUE KEY `uk_active_driver` (`active_driver_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

### 2.3 三个难点的解决

#### 难点 1 的解决：状态与时间——「主表时间戳 + 独立日志表」双写

**方案对比**：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 只在订单表加时间戳列 | 读取快，列表页直接 SELECT 出时间线 | 新增状态节点要 `ALTER TABLE`；无法追溯「谁改的、改了几次」 |
| 只建独立状态日志表 | 灵活可追溯，可扩展 | 每次显示当前状态都要连表取最后一条，列表页性能差 |
| **双写（本系统采用）** | 两者兼得 | 需要保证一致性 |

**实现**：`ride_order` 上冗余 6 个状态时间戳列服务页面渲染；
`ride_order_status_log` 记录每次变更的 `from_status`/`to_status`/`operator_type`/`operator_id`/`changed_at`
服务审计与统计。**两者在同一个事务内写入**，保证一致。

**收益的可验证性**：正因为有这张日志表，系统才能算出「平均等待接单时长」
「平均接驾时长」「平均行程时长」这类指标（见 5.3 节）。这是单靠时间戳列做不到的。

#### 难点 2 的解决：跨表约束——三层防护

`CHECK` 不能跨表，因此「只有车辆可运营才能接单」无法用声明式约束表达。
本系统用**三层防护**替代：

| 层次 | 手段 | 拦截的问题 |
| --- | --- | --- |
| 1. 筛选层 | 视图 `v_available_drivers` | 统一「可接单资格」口径，派单候选只从这里选 |
| 2. 事务层 | 接单事务内 `SELECT ... FOR UPDATE` 锁车辆行 | 「被邀请时车可运营，接单瞬间被改成不可运营」的时序漏洞 |
| 3. 兜底层 | 生成列唯一索引 `uk_active_driver` | 一个司机同时接多单 |

`v_available_drivers` 的判定条件：

```sql
WHERE d.online_status = 1       -- 司机在线
  AND d.status = 1              -- 司机账号正常
  AND d.audit_status = 1        -- 资质已通过审核
  AND a.status = 1              -- 登录账号启用
  AND EXISTS (SELECT 1 FROM vehicle v
               WHERE v.driver_id = d.driver_id AND v.operate_status = 1)  -- 有可运营车辆
  AND NOT EXISTS (SELECT 1 FROM ride_order o                              -- 当前没有进行中订单
                   WHERE o.driver_id = d.driver_id
                     AND o.status IN ('accepted','arrived','in_progress'))
```

> 最后一个条件是**实测后补上的**。最初没有它，结果平台会把订单派给正在跑单的司机，
> 对方一点「接单」就撞上唯一索引被拒，白白浪费一轮派单机会。详见 7.2 节。

**为什么不用触发器做这条业务校验**：触发器抛出的错误信息难以统一为业务语义，
且隐式行为在调试时很难定位。而 `FOR UPDATE` 行锁能精确表达「读-判-写」期间的排他性。

#### 难点 3 的解决：独立派单表

设计 `order_dispatch` 表，`(order_id, driver_id)` 唯一，附带
`status`（invited/accepted/rejected/expired/cancelled）、`batch_no`（第几轮派单）、
`invited_at`/`responded_at` 等**关系属性**。

这张表解决了三个问题：
1. **拒单有了归宿** —— 订单状态不变，只把这条邀请标记为 `rejected`；
2. **多路派单** —— 一个订单可以同时邀请多名司机（本系统默认 3 名）；
3. **派单策略可分析** —— 可以统计各司机的拒单率（见 5.4 节）。

### 2.4 物理结构设计

#### 2.4.1 数据类型选择

| 数据类型 | 应用 | 理由 |
| --- | --- | --- |
| `DECIMAL(10,2)` | 所有金额 | **绝不用 FLOAT/DOUBLE** —— 浮点数无法精确表示小数，多次累加会产生分位误差 |
| `DECIMAL(10,6)` | 经纬度 | 6 位小数约 0.11 米精度；不用浮点避免舍入 |
| `BIGINT UNSIGNED` | 主键、外键 | 订单量可能很大；无符号扩大取值范围一倍 |
| `DATETIME` | 业务时间 | 统一使用数据库端 `NOW()`，避免应用与数据库时钟不一致 |
| `DATETIME(3)` | 轨迹采样时间 | 毫秒精度，满足轨迹排序需求 |
| `TINYINT` + `CHECK` | 状态枚举、标志位 | 比 `ENUM` 灵活（改值不影响表结构），比 `VARCHAR` 省空间 |
| `ENUM` | 订单状态、邀请状态 | 取值集合固定且查询频繁，`ENUM` 存储紧凑且自带约束 |

#### 2.4.2 索引设计

共设计 **30 个二级索引**。设计原则：

1. **复合索引遵循最左前缀原则**
   如 `idx_order_region_status_time(origin_region, status, created_at)`
   可同时服务「按区域查」「按区域+状态查」「按区域+状态+时间排序」三种查询。

2. **等值条件在前，范围条件在后**
   `idx_driver_region_online(region, online_status)` 两个都是等值；
   `idx_rule_type_effective(car_type_id, effective_from, effective_to)` 前等值后范围。

3. **写入密集的表索引越少越好**
   `order_track` 有上万行写入，**只保留一个**复合索引 `(order_id, located_at)`。
   每多一个索引，每次 INSERT 就要多维护一棵 B+ 树。

4. **让索引一物多用**
   实测发现，`idx_vehicle_type_status(car_type_id, operate_status)`
   因为以 `car_type_id` 开头，同时充当了车型外键的支撑索引 ——
   MySQL 因此拒绝直接删除它（`ERROR 1553`）。这说明该索引的成本是"顺带"的，
   因为外键本来就需要一个以 `car_type_id` 开头的索引。

索引优化的实测对比见第六章。

#### 2.4.3 字符集与排序规则

库、表、连接三处统一使用 `utf8mb4` / `utf8mb4_0900_ai_ci`。
`utf8mb4` 是 MySQL 中唯一能完整存储 4 字节字符（如 emoji）的字符集；
`utf8mb4_0900_ai_ci` 是 MySQL 8 的默认排序规则，支持重音不敏感比较。

## 三、系统实现

### 3.1 技术架构

```
┌─────────────────────────────────────────────────┐
│  浏览器（Jinja2 服务端渲染的 HTML + 原生 JS）      │
└────────────────────┬────────────────────────────┘
                     │ HTTP
┌────────────────────▼────────────────────────────┐
│  FastAPI 路由层（按角色划分）                      │
│   /auth/*  /passenger/*  /driver/*  /admin/*    │
└────────────────────┬────────────────────────────┘
┌────────────────────▼────────────────────────────┐
│  服务层 services/                                 │
│   事务边界 · 状态机 · 并发控制 · 存储过程调用        │
└────────────────────┬────────────────────────────┘
┌────────────────────▼────────────────────────────┐
│  数据访问层 repositories/（纯手写参数化 SQL）       │
└────────────────────┬────────────────────────────┘
┌────────────────────▼────────────────────────────┐
│  MySQL 8.4                                        │
│  表 · 视图 · 存储函数 · 存储过程 · 触发器 · 事务    │
└─────────────────────────────────────────────────┘
```

**分层原则**：
- 数据访问层只写 SQL，不含业务规则；
- 服务层负责事务边界、状态机流转与并发控制；
- 涉及原子性的多步操作（下单、接单、结算）下沉到**存储过程**，
  保证任何调用方都走同一条正确路径。

### 3.2 关键实现

#### 3.2.1 计价：存储函数作为唯一真相来源

```sql
CREATE FUNCTION `fn_calc_fare`(
    p_base_price, p_base_distance_km, p_per_km_price,
    p_per_min_price, p_min_price, p_distance_km, p_duration_min
) RETURNS DECIMAL(10,2) DETERMINISTIC NO SQL
BEGIN
    SET v_fare = p_base_price
               + GREATEST(0, p_distance_km - p_base_distance_km) * p_per_km_price
               + p_duration_min * p_per_min_price;
    IF v_fare < p_min_price THEN SET v_fare = p_min_price; END IF;
    RETURN ROUND(v_fare, 2);
END
```

把计价做成数据库里的函数，好处是：下单估价、行程结算、报表核算、
页面上展示的公式说明，**全部调用同一个函数**，不会出现
「前后端各算一套、结果对不上」的情况。实测 757 条已完成订单的车费
与按快照重算的结果**完全一致，零差异**。

#### 3.2.2 价格快照：让历史订单免受调价影响

下单时（`sp_create_order` 内），把当前生效规则的五个价格复制进订单行：

```sql
SELECT r.rule_id, r.version, r.base_price, r.base_distance_km,
       r.per_km_price, r.per_min_price, r.min_price
  INTO v_rule_id, v_rule_version, ...
  FROM `v_pricing_current` r
 WHERE r.car_type_id = p_car_type_id
 ORDER BY r.version DESC LIMIT 1;

INSERT INTO `ride_order` (..., `pricing_rule_id`, `rule_version`,
    `snap_base_price`, `snap_base_distance_km`, `snap_per_km_price`,
    `snap_per_min_price`, `snap_min_price`, ...) VALUES (...);
```

行程结束结算时，只用订单自己的快照列：

```sql
SELECT `fn_calc_fare`(o.`snap_base_price`, o.`snap_base_distance_km`,
                      o.`snap_per_km_price`, o.`snap_per_min_price`,
                      o.`snap_min_price`, p_distance_km, p_duration_min)
  INTO p_fare_amount FROM `ride_order` o WHERE o.`order_id` = p_order_id;
```

配套的**版本化纪律**：改价时绝不 `UPDATE` 已生效行的单价列，
而是新增一个版本行，并把旧行的 `effective_to` 设为新版本生效时刻。

#### 3.2.3 并发接单：条件更新 + 影响行数判定

```sql
START TRANSACTION;

-- 第 1 层（最先执行）：条件抢占
UPDATE `ride_order`
   SET `status` = 'accepted', `driver_id` = p_driver_id, `accepted_at` = NOW()
 WHERE `order_id` = p_order_id
   AND `status`   = 'pending';          -- ← 并发守卫

-- ROW_COUNT() = 1 → 抢到，继续；= 0 → 已被别人接走，ROLLBACK
```

**原理**：该 `UPDATE` 会先对目标行加排他行锁。并发事务二在此阻塞，
待事务一提交后重新读取，发现 `status` 已不是 `pending`，匹配 0 行而干净退出。

**关键纪律**：必须判断 `ROW_COUNT()`，
**绝不能写成「先 SELECT 查状态，再无条件 UPDATE」** —— 那样两步之间存在竞态窗口。

> 这个方案中「把条件 UPDATE 放在最前面」这一点是**实测出来的**，
> 最初的实现顺序相反，导致 5 并发下稳定死锁。详见 7.1 节。

**`v_order_detail` 示例**（把状态映射封装在数据库层，避免每个页面各写一套 `CASE`）：

```sql
CASE o.`status`

    WHEN 'accepted'    THEN '已接单'

```

### 4.2 存储函数与存储过程

**1 个存储函数**（`fn_calc_fare`，见 3.2.1）+ **6 个存储过程**：

| 过程 | 事务内完成的操作 |
| --- | --- |
| `sp_create_order` | 取当前规则 → 价格快照 → 建订单 → 回填订单号 → 写首条状态日志 |
| `sp_dispatch_order` | 校验可派 → 算批次号 → 从 `v_available_drivers` 选候选 → 批量写邀请 |
| `sp_accept_order` | 邀请校验 → 条件抢占 → 资格复检(行锁) → 回填车辆 → 撤销其他邀请 → 写日志 |
| `sp_complete_order` | 状态校验 → 调 `fn_calc_fare` 按快照计价 → 改状态 → 写日志 |
| `sp_cancel_order` | 状态守卫 → 改状态 → 写日志 → 关闭未应答邀请 |
| `sp_expire_dispatch` | 批量把超时未应答的邀请置为 expired |

**为什么把逻辑放进存储过程**：接单涉及四步操作，必须是原子操作。
放在数据库里可以保证**任何调用方（Web 界面、测试脚本、手工 SQL）
都走同一条正确路径**，不会因为某个调用方漏了一步而产生不一致数据。

### 4.3 触发器（1 个）

`trg_review_after_insert`：插入评价后维护司机的服务分与评价数。

```sql
UPDATE `driver` d
   SET d.`service_score` = (SELECT ROUND(AVG(r.`score`), 2)
                              FROM `order_review` r
                             WHERE r.`driver_id` = NEW.`driver_id`),
       d.`review_count`  = (SELECT COUNT(*)
                              FROM `order_review` r
                             WHERE r.`driver_id` = NEW.`driver_id`)
 WHERE d.`driver_id` = NEW.`driver_id`;
```

**做法是在触发器里回读 `order_review` 求精确均值**，结果与 `ROUND(AVG(score), 2)` 严格相等。

> **纠正一个常见误解**：MySQL 只禁止触发器**修改**它所在的那张表
> （`ERROR 1442`），**并不禁止读取**。实测确认：在 `AFTER INSERT` 触发器里
> `SELECT` 本表，新插入的行已经可见，求出的均值天然包含本次评价，无需特判。

**为什么最终没有用增量公式**（详见 7.7 节）：增量公式
`新均值 = (旧均值 × 旧评价数 + 本次评分) ÷ (旧评价数 + 1)`
每一步都要 `ROUND`，误差逐次累积，实测 15 条评价就产生了 0.02 的偏差，
导致一致性校验失败。

**性能权衡**：回读是 O(n)、增量是 O(1)。本场景每次只扫该司机的评价行
（几十条），代价可忽略；正确性远比这点开销重要。

**正确性验证**：视图 `v_driver_service_score` 同时给出「触发器维护值」与
「实时聚合值」，管理端页面直接对比。实测 24 名有评价的司机**全部严格相等**。

**刻意没有用触发器的地方**：不用触发器写订单状态日志。
因为触发器拿不到「谁操作的」这一上下文，需要靠 `SET @变量` 传递会话状态，脆弱且难调试。
状态日志改由应用层在同一事务内显式写入，`operator_type`/`operator_id` 准确可靠。

### 4.4 事务

必须包在事务里的操作：下单、接单、拒单、行程推进、完成结算、取消、
派单批次生成、计价规则版本切换。

应用层用上下文管理器统一管理事务边界：

```python
@contextmanager
def transaction(conn):
    cur = conn.cursor()
    try:
        yield cur
        conn.commit()
    except Exception:
        conn.rollback()
        raise
    finally:
        cur.close()
```

这样杜绝了两个经典错误：忘记 commit 导致数据丢失、
异常时忘记 rollback 导致长时间持锁。

## 六、性能分析与索引优化

### 6.1 实验方法

`sql/02_indexes.sql` 刻意与建表脚本分开，就是为了做对照实验：

1. 只执行 `00 + 01`（此时仅有主键/唯一键/外键索引），跑查询并记录 `EXPLAIN`；
2. 执行 `02` 建立二级索引，再次 `EXPLAIN`；
3. 对比 `type`（访问类型）、`key`（实际使用的索引）、`rows`（预估扫描行数）。

### 6.2 实测对比结果

| 查询 | 优化前 | 优化后 |
| --- | --- | --- |
| **Q1 待接单池**<br>`WHERE status='pending' ORDER BY created_at DESC` | `type=ALL`<br>`key=NULL`<br>`rows=900`<br>**Using filesort** | `type=ref`<br>`key=idx_order_status_created`<br>`rows=44`<br>（无 filesort） |
| **Q2 按区域派单候选**<br>`WHERE origin_region=? AND status='pending'` | `type=ALL`<br>`key=NULL`<br>`rows=900`<br>**Using filesort** | `type=ref`<br>`key=idx_order_region_status_time`<br>`rows=4` |
| **Q3 司机资格筛选**<br>`WHERE region=? AND online_status=1` | `type=ALL`<br>`key=NULL`<br>`rows=35` | `type=ref`<br>`key=idx_driver_region_online`<br>`rows=1` |
| **Q4 取当前计价规则** | `type=ref`<br>`key=uk_rule_type_version`<br>`rows=1` | `type=ref`<br>`key=uk_rule_type_version`<br>`rows=1`（**未变化**） |
| **Q5 乘客订单列表** | 索引被外键占用，无法删除 | 同左 |

### 6.3 结果分析

**（1）索引效果最显著的是消除全表扫描与文件排序**

Q1 从 `type=ALL`（全表扫描 900 行）+ `Using filesort`（额外排序）变为
`type=ref`（索引查找 44 行）且排序由索引天然提供。
`filesort` 的消除往往比减少扫描行数更有价值 —— 它意味着数据库不必
把结果集全部取出后在内存里重排。

**（2）复合索引的最左前缀让一个索引服务多种查询**

Q2 中 `idx_order_region_status_time(origin_region, status, created_at)`
同时提供了「区域等值 + 状态等值 + 时间排序」三件事，
扫描行数从 900 降到 4，且没有 filesort。

**（3）索引不是建了就会被用 —— Q4 是一个诚实的反例**

本系统为「取当前计价规则」专门建了 `idx_rule_type_effective(car_type_id, effective_from, effective_to)`，
但**实测中优化器两次都选择了唯一键 `uk_rule_type_version(car_type_id, version)`**，
没有使用这个专用索引。

原因：`uk_rule_type_version` 已提供 `car_type_id` 前缀，
而当前每个车型只有 1 个版本，通过 `car_type_id` 过滤后只剩 1 行，
后续的时间窗条件过滤成本可忽略。优化器的选择是合理的。

**结论**：`idx_rule_type_effective` 在当前数据规模下**收益不明显**。
若每个车型积累了几十个历史版本，该索引才会体现出价值。
这是一个值得记录的判断：**索引应当基于实际执行计划来评估，而非凭直觉添加**。

**（4）有些索引"删不掉"，因为它在兼两职**

实验中尝试删除 `idx_vehicle_type_status`、`idx_order_passenger_status_time`、
`idx_order_driver_status_time`、`idx_order_car_type` 时，
MySQL 报错 `ERROR 1553: Cannot drop index: needed in a foreign key constraint`。

原因是这些复合索引的**首列**恰好是外键列（`car_type_id`、`passenger_id`、`driver_id`），
InnoDB 用它们来支撑外键约束。这说明这些索引的成本是"顺带"的 ——
即使不为查询优化，外键本身也需要一个以该列开头的索引。

**（5）Q5 未能完成对照**

`idx_order_passenger_status_time` 因同时支撑 `passenger_id` 外键而无法删除，
因此无法做优化前后的对比。这是实验设计上的一个限制，
但也从侧面说明了该索引的必要性。

## 七、问题与解决过程

本章记录设计过程中**实测发现的六个真实缺陷**。它们都不是笔误，
而是对 MySQL 行为理解不足导致的，解决过程都有明确的诊断证据。

### 7.1 并发接单死锁（ERROR 1213）

**现象**：5 个司机并发抢同一订单时，正确性没问题（始终只有 1 人成功），
但 4 个落败者中有 3 个拿到的是 `DB_ERROR_1213`（死锁），
而不是设计的 `ALREADY_TAKEN` 干净失败路径。

**诊断过程**：

第一步，把存储过程里笼统的 `DB_ERROR` 改为捕获真实错误码。
但改完后错误码显示为 `DB_ERROR_0`、错误消息为空 —— 说明诊断代码本身有问题。

第二步，做对照实验定位：

```sql
-- 变体 A：变量声明在 handler 的 BEGIN...END 内部
DECLARE EXIT HANDLER FOR SQLEXCEPTION
BEGIN
    DECLARE v INT DEFAULT 0;
    GET DIAGNOSTICS CONDITION 1 v = MYSQL_ERRNO, ...;
END;

-- 变体 B：变量声明在过程主体
DECLARE v INT DEFAULT 0;
DECLARE EXIT HANDLER FOR SQLEXCEPTION
BEGIN
    GET DIAGNOSTICS CONDITION 1 v = MYSQL_ERRNO, ...;
END;
```

| 变体 | 结果 |
| --- | --- |
| A（handler 内声明） | `errno=0`，消息为空 ❌ |
| B（主体声明） | `errno=1146`，消息正确 ✓ |

**这是第一个发现**：`GET DIAGNOSTICS` 不会填充在 handler 块内部声明的变量。

第三步，修正诊断代码后拿到真实错误：

```
接单失败[1213]：Deadlock found when trying to get lock; try restarting transaction
```

第四步，从 InnoDB 取死锁详情：

```sql
SHOW ENGINE INNODB STATUS\G   -- 查看 LATEST DETECTED DEADLOCK 段
```

报告显示：

```
*** (1) TRANSACTION:
UPDATE `ride_order` SET `status`='accepted', ... WHERE `order_id`=? AND `status`='pending'
*** (1) HOLDS THE LOCK(S):
RECORD LOCKS ... table `taxi_system`.`driver` ... lock_mode X locks rec but not gap
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... table `taxi_system`.`ride_order` ... lock_mode X locks rec but not gap waiting
```

**根因**：事务持有 `driver` 表的行锁，同时在等待 `ride_order` 的行锁 ——
各事务在两张表之间**交叉持锁形成循环等待**。

**为什么会这样**：最初的实现顺序是
「先 `SELECT ... FOR UPDATE` 锁 driver/vehicle → 再 `UPDATE ride_order`」。
5 个事务同时这样做，各自先拿到自己司机的 `driver` 行锁，然后都去抢同一行 `ride_order`，
形成等锁环。

**修复**：调整加锁顺序，**把条件 UPDATE 提到最前面**。

```
修复前：锁 driver/vehicle → 抢 ride_order     （交叉持锁，死锁）
修复后：抢 ride_order → 锁 driver/vehicle     （竞争在第一步就串行化）
```

修复后，只有一个事务能通过第一步并继续往下走，
其余事务在该处等待，醒来时匹配 0 行而干净退出，
**根本不会去申请 driver/vehicle 的锁**，死锁环无从形成。

**修复效果**：4 名落败者全部返回干净的 `ALREADY_TAKEN`，耗时 0.59 秒，无一死锁。

### 7.2 派生列在批量导入时被重复累加

**现象**：全库不变量检查发现，**24 名有评价的司机的 `service_score` 与
`review_count` 全部与实时聚合值不一致**，且 `review_count` **恰好是真实评价数的 3 倍**。

**诊断**：3 倍这个数字很可疑 —— 不是随机漂移，而是系统性重复。
排查后确认只有 1 个触发器，`order_review` 表也只有 357 行（正确）。

**根因**：`driver.service_score` 与 `driver.review_count` 是**由触发器从 `order_review` 派生的冗余列**。
而 `06_seed_demo.sql` 是 `mysqldump` 导出的，**把这两列连同计算结果一起写进了 SQL**。
导入时：driver 行带着导出时刻的计算结果进来，
随后 `order_review` 的批量插入**又触发一次触发器重复累加**。
导入一次翻一倍，导入三次就是三倍。

**修复**：**派生列不进快照，批量导入后由源数据重算**。
在 `06_seed_demo.sql` 末尾追加一段"派生列重建"：

```sql
UPDATE `driver` d
   SET d.`review_count` = (SELECT COUNT(*) FROM `order_review` r
                            WHERE r.`driver_id` = d.`driver_id`),
       d.`service_score` = IFNULL((SELECT ROUND(AVG(r.`score`), 2)
                                     FROM `order_review` r
                                    WHERE r.`driver_id` = d.`driver_id`), 5.00);
```

修复后 `SUM(review_count)` 与 `COUNT(order_review)` 完全一致。

**这个问题的普遍性**：任何「用触发器维护冗余列」的表，
在导出/恢复时都会遇到同样的问题。正确处理方式就是**派生列不入快照、恢复后重算**。

### 7.3 存储生成列的基列不能用级联外键

**现象**：建表时报 `ERROR 1215: Cannot add foreign key constraint`。

**诊断思路**：错误出现在 `CREATE TABLE ride_order` 第一条语句上。
逐条排查外键后发现，问题出在 `fk_order_driver` 的 `ON UPDATE CASCADE`。

**根因**：`driver_id` 是**存储生成列 `active_driver_id` 的基列**。
MySQL 规定：**基列的外键不得使用 `ON UPDATE CASCADE` / `ON DELETE SET NULL`**。
原因是级联动作由存储引擎直接修改数据行，会**跳过生成列的重新计算**，
导致 `active_driver_id` 与实际状态不一致。

**修复**：把 `fk_order_driver` 改为 `ON UPDATE RESTRICT ON DELETE RESTRICT`。
`driver_id` 是代理主键、从不更新，语义上没有任何损失。

```sql
-- ⚠️ driver_id 是存储生成列 active_driver_id 的「基列」，
--    MySQL 规定：基列的外键不得使用 ON UPDATE CASCADE / ON DELETE SET NULL
CONSTRAINT `fk_order_driver` FOREIGN KEY (`driver_id`) REFERENCES `driver` (`driver_id`)
    ON UPDATE RESTRICT ON DELETE RESTRICT,
```

### 7.4 自动派单会把订单派给正在跑单的司机

**现象**：端到端流程测试中，司机接单失败，返回 `DRIVER_BUSY`。
排查发现被选中的司机已有一单「行程中」。

**诊断**：这其实是**数据库层兜底防线正确生效**（`uk_active_driver` 拦住了第二单），
但暴露了**上游的一个真实缺口**：`v_available_drivers` 视图只检查
「在线 + 已审核 + 有可运营车辆」，**没有排除正在跑单的司机**。

后果是：平台会把订单派给一个根本接不了的人，对方一点「接单」就被拒，
白白浪费一轮派单机会，用户体验很差。

**修复**：在 `v_available_drivers` 中补上「当前没有进行中订单」的条件。

修复后 `DRIVER_BUSY` 从**常态**退化为**纯粹的并发竞态兜底**
（例如：邀请发出后、司机应答前，他恰好被并发地分配了另一单）。

**连带发现**：排查过程中还发现演示数据本身不合理 ——
30 名司机中有 24 名同时在载客（占车队 80%），导致在线运力被吃空。
这是数据生成器的缺陷：它把「进行中订单数」按有资格司机数分配，
而没有考虑这些订单的时间戳是「此刻」、属于**并发**在跑。
修正为**限制在运力池的 25% 以内**后，可接单司机恢复到 15 名，符合真实情况。

### 7.5 模板中的 NULL 比较导致整页 500

**现象**：区域供需统计页 `/admin/regions` 返回 500。

**根因**：模板中写了

```jinja
{% set tight = supply_demand | selectattr('demand_supply_ratio', 'gt', 20) | list %}
```

而「在线司机数为 0 的区域」其供需比在 SQL 中返回 `NULL`，
Jinja2 执行 `None > 20` 直接抛 `TypeError`。

**修复**：先剔除 NULL 再比较。

```jinja
{% set tight = supply_demand
    | selectattr('demand_supply_ratio', 'ne', None)
    | selectattr('demand_supply_ratio', 'gt', 20) | list %}
```

**教训**：SQL 中的 `NULL` 语义（`NULL > 20` 结果是 `UNKNOWN` 而非 `False`）
会一路传递到模板层并变成运行时异常。凡是可能为空的聚合结果，
在模板中使用前都应先做空值处理。

### 7.6 演示数据声称"可复现"，实际不可复现

**现象**：演示数据生成器声明使用固定随机种子、结果可复现。
但为了写演示脚本而连续生成两次后，订单状态分布出现了差异：

```
第 1 次：completed=758, accepted=3
第 2 次：completed=757, accepted=4      ← 差 1 条
```

**诊断**：`random.seed(RANDOM_SEED)` 确实设置了，Python 侧的随机序列是确定的。
问题出在**随机性依赖了数据库返回的行序**，而这个行序本身不保证稳定：

```python
cur.execute(
    "SELECT d.driver_id, d.region FROM driver d "
    " JOIN vehicle v ON ... WHERE ... GROUP BY d.driver_id, d.region"
)                      # ← 没有 ORDER BY
eligible = cur.fetchall()

drv = random.choice(eligible)        # ← 行序一变，选中的司机就变了
random.shuffle(pool)
```

MySQL **不保证无 `ORDER BY` 的 `GROUP BY` 返回行序稳定**。
行序一变，即使随机种子相同，`random.choice` 和 `random.shuffle` 的结果也会不同。

还有第二处同类问题：

```python
"SELECT ... FROM ride_order WHERE status='completed' ORDER BY RAND() LIMIT 600"
```

`RAND()` 是 **MySQL 自己的伪随机数发生器**，不受 Python 的 `random.seed()` 控制，
每次运行抽到的订单都不同。

**修复**：

1. 在 `eligible` 查询末尾加 `ORDER BY d.driver_id`，让行序确定；
2. 把 `ORDER BY RAND() LIMIT 600` 改为按 `order_id` 有序取出后，
   在 Python 侧用 `random.sample()` 抽样。

**验证**：连续生成两次，订单状态分布、评价数、派单记录数、轨迹点数、
状态日志数**全部完全一致**：

```
第 1 次：pending=42, accepted=4, arrived=1, in_progress=1, completed=757, cancelled=95
        评价 343 / 派单 3383 / 轨迹 12391 / 日志 4032
第 2 次：pending=42, accepted=4, arrived=1, in_progress=1, completed=757, cancelled=95
        评价 343 / 派单 3383 / 轨迹 12391 / 日志 4032
```

**教训**：**「设置了随机种子」不等于「结果可复现」**。
只要随机选择依赖了任何外部的不确定输入 —— 数据库行序、哈希遍历顺序、
文件系统顺序、时间 —— 复现性就被破坏了。
凡是要对顺序敏感的随机选择，必须显式指定排序。
本项目的演示脚本、测试断言都依赖具体数据，这个修复是必要的。

### 7.7 触发器增量公式的舍入误差累积

**现象**：全库一致性检查中，司机 #29（孙艳涛）的 `service_score` 是 4.25，
但直接对 `order_review` 求平均得到的精确值是 4.27，**偏差 0.02**。
管理端的「评价管理」页面因此显示出「不一致」，看起来像系统故障。

**诊断**：该司机有 15 条评价，评分依次为 `1,1,4,4,4` 加十个 `5`，
精确均值 `64 ÷ 15 = 4.2667`。

最初实现的触发器用的是增量公式：

```sql
SET service_score = ROUND((service_score * review_count + NEW.score)
                          / (review_count + 1), 2)
```

**每一步都把结果 `ROUND` 到 2 位小数**，而下一次迭代又拿这个已经舍入过的值继续计算，
误差因此逐步累积。15 步之后累积出 0.02 的偏差，评价越多偏得越远。

用最小可复现案例验证（把 `service_score` 精度放宽到 3 位以减少干扰）：

| 方案 | 计算结果 | 精确值 |
| --- | --- | --- |
| 增量公式 | 4.266 | 4.267 |
| 回读本表求均值 | **4.267** | 4.267 |

**修复过程中纠正了一个错误假设**。

原实现的注释里写着「MySQL 限制触发器读写其自身所在的表，回读有风险」，
因此当初刻意选择了增量公式来规避回读。这次专门做了实验验证这句话是否成立：

```sql
CREATE TRIGGER `zz_trg_exact` AFTER INSERT ON `zz_test_review`
FOR EACH ROW
BEGIN
    UPDATE `zz_test_driver` d
       SET d.`avg_score` = (SELECT ROUND(AVG(r.`score`), 3)
                              FROM `zz_test_review` r
                             WHERE r.`driver_id` = NEW.`driver_id`)
     WHERE d.`id` = NEW.`driver_id`;
END
```

**结果：建触发器成功、执行成功、结果精确。**

结论是：MySQL 只禁止触发器**修改**它所在的那张表
（`ERROR 1442: Can't update table ... already used by statement`），
**并不禁止读取**。当初的顾虑建立在一个不成立的前提上。

**修复**：把触发器改为回读 `order_review` 求精确均值，
并用一条 UPDATE 重建了全部司机的服务分。修复后一致性检查归零，
且新触发器插入评价后的结果与精确均值**严格相等**（实测：插入 1 分评价后
由 4.27 变为 4.06，精确值 4.06）。

**性能权衡**：回读是 O(n)、增量是 O(1)。本场景每次只扫该司机的评价行
（几十条量级），代价可忽略。若评价量真的达到百万级，
更合适的做法是增量维护 + 定期全量重算校正 —— 用 O(1) 换一点点最终一致性，
而不是像原来那样用错误的前提换来一个会漂移的实现。

**教训**：**「为了性能而做的妥协」必须建立在真实约束之上**。
这里当初选择增量公式，理由是一个未经证实的性能顾虑和一个错误的 MySQL 限制认知，
结果付出了正确性的代价。**先验证约束是否真实存在，再决定要不要为它妥协。**

### 8.2 设计亮点

1. **生成列唯一索引强制「一司一单」**
   利用「唯一索引允许多个 NULL」这一特性，让索引只对「进行中」的订单生效，
   在数据库层表达了「一个司机同时最多一个进行中订单」这条业务规则。
   即使应用层逻辑写漏，也插不进第二条。

2. **价格快照 + 规则版本化**
   订单金额自持，规则表怎么改都不影响历史订单；
   同时"只新增版本、不修改已生效行"的纪律保证了规则本身的可追溯性。

3. **状态时间双写**
   时间戳列服务 UI 渲染，日志表服务审计与统计分析。
   实测表明，正是因为有日志表，系统才能算出平均接单时长、接驾时长、行程时长等指标。

4. **三层防护替代无法表达的跨表 CHECK**
   视图筛选 → 行锁复检 → 唯一索引兜底。
   每一层拦截不同的问题，且各层的职责边界清晰。

5. **并发方案的正确性可被证明**
   `UPDATE ... WHERE status='pending'` + 判断 `ROW_COUNT()` 的方案不依赖隔离级别，
   靠行锁与影响行数判定；并且通过多线程测试真实复现了竞争。

6. **数据一致性可被验证**
   视图 `v_driver_service_score` 同时给出「触发器维护值」与「实时聚合值」，
   让冗余设计的正确性成为可检查的事实，而不是需要信任的假设。

### 8.3 收获与反思

**几点体会**：

1. **对数据库行为不能凭直觉假设，必须实测**
   本次发现的六个问题（死锁、派生列重复累加、生成列基列限制、
   `GET DIAGNOSTICS` 作用域、数据生成不可复现、触发器舍入漂移）无一能靠阅读文档预先规避 ——
   都是在真实运行中暴露出来的。尤其是**加锁顺序导致的死锁**，
   只有真跑并发才能发现，顺序执行永远测不出来。

2. **诊断能力比修复能力更重要**
   最初把异常笼统处理为 `DB_ERROR`，等于把最有价值的信息丢掉了。
   正是把错误码一路追到 `1213` 并从 InnoDB 拿到死锁详情，
   才定位到加锁顺序问题。**异常处理应当保留原始信息**。

3. **性能优化要靠执行计划，不能凭直觉**
   `idx_rule_type_effective` 这个索引是凭直觉加的，实测证明优化器并不使用它。
   索引不是越多越好 —— 每个索引都有写入成本，应当基于 `EXPLAIN` 的实际结果来判断。

4. **冗余设计的代价必须被管理**
   服务分用触发器维护是"用空间换时间"，但这次也经历了批量导入导致的漂移。
   任何冗余都需要配套的**一致性校验手段**（本次用视图实现）和**重建手段**。

### 8.4 可改进方向

| 方向 | 说明 |
| --- | --- |
| 分区表 | `order_track` 数据量增长最快，适合按 `located_at` 做 RANGE 分区 |
| 派单算法 | 当前按「同区域 + 车型 + 服务分」，可接入经纬度做球面距离排序 |
| 物化汇总 | `v_order_status_duration` 在大数据量下要全表聚合，可物化为汇总表并定时增量更新 |
| 缓存层 | 会话与热点查询可引入 Redis（本作业刻意不引入外部依赖） |
| 状态存储 | 订单状态用 `ENUM` 新增值需 `ALTER TABLE`，状态常扩展时可改为字典表 |
| 定时任务 | 本机 `event_scheduler` 已开启，可用 MySQL EVENT 实现每日的证照到期扫描与数据归档 |
