## 三、分镜脚本

### 第 0 幕 · 开场（约 30 秒）

**画面**：终端窗口，显示 uvicorn 启动日志。

**操作**：无，让日志自己滚完。

**解说词参考**：
> 这是一个基于 MySQL 8.4 与 FastAPI 实现的网约车系统，覆盖乘客下单、平台派单、
> 司机接单、行程执行、状态追踪到自动计价的完整链路。
> 数据库共设计了 16 张表、6 个视图、1 个存储函数、6 个存储过程和 1 个触发器，
> 所有查询都是手写 SQL，没有使用 ORM。

### 第 1 幕 · 数据库设计（约 2 分钟）

> 这是**数据库课程**作业，建议把数据库部分放在最前面亮出来。

**画面**：终端，切到项目目录。

**操作**：
```bash
# 1. 表清单
mysql -u root -p -e "USE taxi_system; SHOW TABLES;"

# 2. 视图
mysql -u root -p -e "USE taxi_system;
  SELECT TABLE_NAME FROM information_schema.VIEWS WHERE TABLE_SCHEMA='taxi_system';"

# 3. 存储过程与函数
mysql -u root -p -e "USE taxi_system;
  SELECT ROUTINE_TYPE, ROUTINE_NAME FROM information_schema.ROUTINES
   WHERE ROUTINE_SCHEMA='taxi_system';"

# 4. 触发器
mysql -u root -p -e "USE taxi_system;
  SELECT TRIGGER_NAME, EVENT_MANIPULATION FROM information_schema.TRIGGERS
   WHERE TRIGGER_SCHEMA='taxi_system';"

# 5. 打开 ER 图
explorer docs\ER图.md
```

**解说词参考**：
> 系统共 16 张表，按职责分为字典、账号、主体、业务和选做五类。
> 账号部分采用了泛化/特化模型 —— 三种角色共享一张 account 登录表，
> 各自的属性放在自己的档案表里，通过唯一的 account_id 外键建立一对一关系。
>
> 6 个视图把复杂查询在数据库层封装了一次，比如 v_order_detail 负责订单的多表连接
> 和状态中文映射，应用层不用每处都写一遍 JOIN。
>
> 6 个存储过程承担了下单、派单、接单、结算这些必须原子完成的操作。
> 其中接单过程是并发控制的核心。

**如果时间紧**：只跑第 1、4 条命令，其余口头带过。

#### 2.3 司机管理 + 资质审核（40 秒）

**操作**：
1. 点导航「司机」
2. 展示司机列表（服务分、车辆数、审核状态、驾驶证到期）

#### 2.4 车辆管理（30 秒）

**操作**：
1. 点「车辆」
2. 在「运营状态」筛选「可运营」
3. 点某辆车的「置为不可运营」→ 确认

**解说词参考**：
> 需求要求「只有车辆处于可运营状态时才能接单」。
> 这是一条跨表约束 —— 涉及司机在线状态、审核状态、账号状态和车辆运营状态，
> 分属三张表。而 MySQL 的 CHECK 约束不能跨表，所以系统用三层防护来实现它：
> 视图筛资格、事务内行锁复检、唯一索引兜底。
> 把车辆置为不可运营，该司机的接单资格会立即失效。

> ⚠️ **记得点回来**（再点一次「置为可运营」），否则第 4 幕可能选不到这个司机。

#### 2.5 计价规则版本化（50 秒）— ★ 亮点

**操作**：
1. 点「计价规则」
2. 展示上半部分「当前生效的规则」表格（4 个车型）
3. 滚到下半部分「全部版本」
4. 演示发布新版本（**可选，看时间**）：
   - 车型选「经济型」，规则名填 `经济型-演示调价版`
   - 起步价填 `12`（原来是 10），里程单价填 `2.5`（原来是 2.3），其余随便填合理的
   - 点「发布新版本」
5. 回到「全部版本」表，指出：经济型出现了 v2，v1 变成「已停用」且生效期被自动截止

**解说词参考**：
> 计价规则是版本化的。改价时不修改已有的规则行，而是新增一个版本，
> 同时把旧版本的失效时间设为新版本的生效时间 —— 已生效的单价列永远不会被 UPDATE。
> 这样做是为了让历史订单可以完整追溯：每张订单都记录了它用的是哪个版本的规则。
>
> 更关键的是，订单在创建时会把当时的五个价格参数**快照**下来。
> 所以不管是发布新版本还是停用旧版本，历史订单的金额都不会变。

#### 2.8 选做：证照到期提醒（20 秒）

#### 4.3 行程执行（50 秒）— ★ 核心 C3

**操作**（按顺序点）：
1. 点「我已到达上车点」→ 状态变「司机已到达」，时间线新增节点
2. 点「乘客已上车，开始行程」→ 状态变「行程中」
3. 页面出现「结束行程并结算」表单，展示下方的**本单计价快照**表格
4. 里程填 `15.6`，时长填 `32`
5. 点「结束行程并结算」

**解说词参考**：
> 每一步都是一个带状态守卫的条件更新 —— SQL 里写成
> `UPDATE ... WHERE order_id=? AND driver_id=? AND status='期望的状态'`，
> 然后判断影响行数。这样能防止状态被重复推进或跳步。
>
> 结算用的是这张订单自己的价格快照，调用数据库里的计价函数算出来。

6. 结算后页面显示最终车费与完整时间线

#### 4.4 计价核对（20 秒）— ★ 核心 C5

**画面**：切到终端。

```bash
mysql -u root -p -e "USE taxi_system;
  SELECT order_id, distance_km, duration_min, fare_amount,
         fn_calc_fare(snap_base_price, snap_base_distance_km, snap_per_km_price,
                      snap_per_min_price, snap_min_price, distance_km, duration_min) AS 函数重算
    FROM ride_order WHERE status='completed' ORDER BY order_id DESC LIMIT 1;"
```

**解说词参考**：
> 里程 15.6 公里、时长 32 分钟。经济型的计价规则是：起步价 10 元含 3 公里，
> 超出部分每公里 2.3 元，每分钟 0.4 元。
>
> 手工算一遍：起步价 10.00，加上超出里程 12.6 公里乘 2.30 等于 28.98，
> 加上时长 32 分钟乘 0.40 等于 12.80，合计 **51.78 元**。
> 数据库函数重算的结果和订单里存的金额完全一致。

### 第 5 幕 · 评价与闭环验证（约 1 分钟）

**画面**：中间窗口（乘客端）。

**操作**：
1. 用 `p001` / `123456` 打开刚完成的订单
2. 点「评价这次行程」
3. 选 5 星，勾选「准时」「态度好」，填评价内容
4. 提交

**画面**：切到左侧窗口（管理端）。

5. 点「评价」→ **滚到「司机服务分」表格**
6. 指出有两列分数：**触发器维护分** 和 **实时聚合分**，以及「一致性」列显示「一致」

**解说词参考**：
> 这里有个设计验证点。司机表上的服务分是一个**冗余的派生列**，
> 由数据库触发器在每次新增评价时维护，避免每次查询都做全表聚合。
>
> 但冗余就有漂移的风险，所以这个页面同时列出「触发器维护的值」和
> 「直接对评价表求平均得到的值」做对比。两列一致，就说明触发器算得对。
>
> 这个校验还真的抓到过两次问题 —— 一次是演示数据批量导入时，
> 派生列被重复累加过，评价数变成了真实值的 3 倍；
> 另一次是触发器的增量公式有舍入误差累积，15 条评价就差出 0.02 分。
> 两次都是靠这个对比发现的。

### 第 6 幕 · 亮点专题（约 3 分钟，时间紧可砍）

#### 6.1 并发抢单验证（2 分钟）— ★ 最能加分

**画面**：终端。

**操作**：
```bash
F:/pythonnewversion/py39ver/python.exe scripts/concurrency_test.py
```

让输出完整展示出来（约 1 秒跑完，可以重跑一次让观众看清）。

**解说词参考**：
> 这段脚本用 5 个线程，各自独立的数据库连接，在同一瞬间抢同一笔订单。
>
> 结果是：1 名司机接单成功，另外 4 名拿到"订单已被其他司机接走"。
> 关键在于这 4 条失败都是**干净的失败**，不是数据库异常。
> 它们走的是设计的路径：SQL 里用 `UPDATE ... WHERE status='pending'`
> 加判断影响行数，行锁让并发事务自动排队，先提交者胜出。
>
> 第三项测试验证的是数据库层的兜底：生成列唯一索引。
> 订单表上有一个生成列，当订单处于进行中状态时它等于司机 ID，否则是 NULL。
> 由于唯一索引允许多个 NULL，这个索引只对进行中的订单生效，
> 在数据库层强制一个司机同时最多一单。

> 💡 **如果被问到"这有什么难的"**：可以说，最初版本的实现是先锁司机表、
> 再更新订单表，5 并发下稳定死锁，后来从 InnoDB 的死锁报告里定位到是加锁顺序问题，
> 把订单表的更新提前才解决。这段经历写在实验报告第七章。

#### 6.2 价格快照验证（1 分钟）

3. 指出：价格快照仍是 v1 的 10.00，车费没变

**解说词参考**：
> 平台刚刚调了价，但刚才那笔已完成订单的金额纹丝不动。
> 因为它的车费只依赖下单时快照下来的规则版本，与规则表当前状态无关。
> 这就是历史订单金额可追溯的做法。
