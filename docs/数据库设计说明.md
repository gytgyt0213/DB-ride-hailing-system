## 一、设计原则与全局约定

| 项 | 约定 | 理由 |
| --- | --- | --- |
| 存储引擎 | `InnoDB` | 需要事务与行级锁支持并发接单 |
| 字符集 | `utf8mb4` / `utf8mb4_0900_ai_ci` | 库、表、连接三处一致，避免中文乱码；utf8mb4 可存 emoji |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT`（字典表用自然键） | 订单量可能很大；无符号扩大取值范围 |
| 金额 | `DECIMAL(10,2)` | **绝不用 FLOAT/DOUBLE** —— 浮点数无法精确表示小数，累计会产生分位误差 |
| 经纬度 | `DECIMAL(10,6)` | 6 位小数约 0.11 米精度，足够；不用浮点避免舍入问题 |
| 时间 | `DATETIME`（轨迹表 `DATETIME(3)`） | 统一用数据库端 `NOW()`，避免应用与数据库时区/时钟不一致 |
| 标识符 | 全部加反引号 | `order`、`rank`、`interval` 等是 MySQL 保留字；订单表因此命名为 `ride_order` |
| 外键删除策略 | 默认 `ON DELETE RESTRICT` | 防止误删历史数据；仅订单的强附属子表用 `CASCADE` |
| 命名 | 表名小写下划线；索引 `idx_` 前缀，唯一索引 `uk_`，约束 `ck_`/`fk_` | 本机 `lower_case_table_names=1`，表名会强制小写，故统一小写命名 |

### 本机 sql_mode 带来的硬约束

执行 `SELECT @@sql_mode` 得到：

```
ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,
ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION
```

- **`ONLY_FULL_GROUP_BY`**：`SELECT` 中的非聚合列必须完整出现在 `GROUP BY` 中。
  本系统所有统计查询与视图定义均按此编写，不能用「随便取一行的值」这种写法。
- **`STRICT_TRANS_TABLES`**：`INSERT` 必须显式列出列名并给全所有 NOT NULL 且无默认值的列；
  空字符串不能写入 `DATE`/`DECIMAL` 列；超范围写入直接报错而非静默截断。

1. 把该车型当前有效旧行的 `effective_to` 设为新版本生效时刻、`status` 置 0；
2. 插入 `version + 1` 的新行。

这样历史订单引用的旧规则行永远不会被篡改，可完整追溯。

**订单状态机**

```
pending（待接单） → accepted（已接单） → arrived（司机已到达） → in_progress（行程中） → completed（已完成）
     ↓                    ↓                    ↓
     └────────────────────┴────────────────────┴──→ cancelled（已取消）
```

**生成列与唯一索引（本设计的关键创新点）**

```sql
`active_driver_id` BIGINT UNSIGNED
    GENERATED ALWAYS AS (
        CASE WHEN `status` IN ('accepted','arrived','in_progress')
             THEN `driver_id` ELSE NULL END
    ) STORED,
UNIQUE KEY `uk_active_driver` (`active_driver_id`)
```

原理：非「进行中」类订单该列的值为 `NULL`，而 SQL 唯一索引**允许多个 NULL**，
因此这个索引只对「进行中」的订单生效，在**数据库层**强制
「一个司机同时最多一个进行中订单」。即使应用层逻辑写漏，也插不进第二条。

> ⚠️ **实现约束**：`driver_id` 是存储生成列的**基列**，MySQL 规定基列的外键
> **不得使用 `ON UPDATE CASCADE` / `ON DELETE SET NULL`**（级联由存储引擎直接改行，
> 会跳过生成列的重新计算）。因此 `fk_order_driver` 只能用 `RESTRICT`。
> `driver_id` 是代理主键、从不更新，语义上无任何损失。
> 这个问题是实测建表时报 `ERROR 1215` 才发现的。

## 三、约束设计

### 3.1 约束类型与分布

| 约束类型 | 数量 | 典型用途 |
| --- | --- | --- |
| PRIMARY KEY | 16 | 每表主键 |
| FOREIGN KEY | 24 | 维护引用完整性 |
| UNIQUE | 11 | 用户名、车牌、身份证、一单一评、生成列 |
| CHECK | 30+ | 枚举取值、数值范围、经纬度范围、时间窗 |
| NOT NULL | 全部必要字段 | 严格模式下强制显式赋值 |

### 3.2 CHECK 约束的能力边界

MySQL 8.0.16+ 才真正执行 CHECK（8.4 完全支持）。但 **CHECK 不能跨表、跨行**。
本系统中有一类需求天然是跨表规则：

> **需求 6：只有车辆处于可运营状态时才能接单。**

这涉及 `driver.online_status`、`driver.audit_status`、`account.status`、
`vehicle.operate_status` 四个字段，分属三张表，**CHECK 无法表达**。

**本系统的解法（三层防护）**：

| 层 | 手段 | 作用 |
| --- | --- | --- |
| 1. 筛选层 | 视图 `v_available_drivers` | 统一「可接单资格」口径，派单候选只从这里选 |
| 2. 事务层 | 接单事务内 `SELECT ... FOR UPDATE` | 锁住车辆行，保证「被邀请 → 接单」期间资格不失效 |
| 3. 兜底层 | 生成列唯一索引 `uk_active_driver` | 数据库层保证一司一单 |

**为什么不用触发器做这条业务校验**：触发器抛出的错误信息难以统一为业务语义，
且隐式行为调试困难。**为什么用 FOR UPDATE**：如果只做普通查询，会出现
「被邀请时车是可运营的，接单瞬间管理员把车改成不可运营」的时序漏洞；
加行锁后，管理员改车辆状态的事务必须等待接单事务提交。

### 4.2 设计原则

- **复合索引遵循最左前缀**：如 `idx_order_region_status_time(origin_region, status, created_at)`
  可服务「按区域查」「按区域+状态查」「按区域+状态+时间排序」三种查询。
- **等值条件在前、范围条件在后**：`(region, online_status)` 两个都是等值；
  `(car_type_id, effective_from, effective_to)` 前一个是等值、后两个是范围。
- **写入密集的表索引越少越好**：`order_track` 有上万行写入，因此**只保留一个**复合索引。
  每多一个索引，每次 INSERT 就要多维护一棵 B+ 树。
- **外键自动创建索引**：InnoDB 会为外键列自动建索引（若无合适的前缀索引）。

### 4.3 索引优化实验方法

`02_indexes.sql` 刻意与 `01_create_tables.sql` **分开**，就是为了做对照实验：

1. 只执行 `00 + 01`（此时仅有主键/唯一键/外键索引），跑 `07_queries_demo.sql` 第八节并记录 `EXPLAIN`；

## 五、视图设计

共 **6 个视图**，定位是把「多表连接 + 状态映射 + 聚合统计」在数据库层封装一次，
应用层直接 `SELECT`，避免每个页面各写一套 JOIN。

| 视图 | 作用 | 关键点 |
| --- | --- | --- |
| `v_order_detail` | 订单全息视图 | 连接订单/乘客/司机/车辆/车型，并把英文状态映射为中文 |
| `v_available_drivers` | 具备接单资格的司机 | 账号启用+司机正常+已审核+在线+有可运营车+无进行中订单 |
| `v_pricing_current` | 各车型当前生效规则 | 封装时间有效窗判定 `effective_from <= NOW()` 且未失效 |
| `v_order_status_duration` | 各节点耗时 | 从状态日志用条件聚合算出等待接单/接驾/行程/全流程耗时 |
| `v_driver_service_score` | 司机服务分 | **同时给出触发器维护值与实时聚合值，用于一致性校验** |
| `v_expiring_licenses` | 证照到期清单 | `UNION ALL` 统一三种证照结构，`DATEDIFF` 算剩余天数 |

**`v_available_drivers` 的一个设计修正**：最初只检查「在线 + 已审核 + 有可运营车」，
实测发现平台会把订单派给**正在跑单的司机**（demo 数据中 30 名司机有 24 名同时在载客），
对方一点「接单」就撞上 `uk_active_driver` 被拒，白白浪费一轮派单机会。
补上 `NOT EXISTS (进行中订单)` 后，`DRIVER_BUSY` 退化为纯粹的并发竞态兜底而非常态。

## 六、存储函数与存储过程

### 6.1 `fn_calc_fare` —— 计价存储函数

```sql
CREATE FUNCTION `fn_calc_fare`(
    p_base_price DECIMAL(10,2), p_base_distance_km DECIMAL(6,2),
    p_per_km_price DECIMAL(10,2), p_per_min_price DECIMAL(10,2),
    p_min_price DECIMAL(10,2),
    p_distance_km DECIMAL(8,3), p_duration_min DECIMAL(8,2)
) RETURNS DECIMAL(10,2) DETERMINISTIC NO SQL
```

**公式**：

```
车费 = 起步价
     + MAX(0, 里程 − 起步含里程) × 里程单价
     + 时长 × 时长单价
车费 = MAX(车费, 最低消费)
```

**设计意图**：把计价做成数据库里的**唯一真相来源**。
下单估价、结算、报表核算、页面上展示的公式说明，全部调用同一个函数，
不会出现「前后端各算一套、结果对不上」的情况。
声明 `DETERMINISTIC NO SQL` 使其可安全用于 binlog 环境。

### 6.2 存储过程一览

| 过程 | 职责 | 事务内完成的步骤 |
| --- | --- | --- |
| `sp_create_order` | 下单 | 取当前有效规则 → **价格快照** → 插订单 → 回填订单号 → 写首条状态日志 |
| `sp_dispatch_order` | 派单 | 校验订单可派 → 算批次号 → 从 `v_available_drivers` 选候选 → 批量写邀请 |
| `sp_accept_order` | **接单（并发核心）** | 邀请校验 → **条件抢占** → 资格复检(行锁) → 回填车辆 → 撤销其他邀请 → 写日志 |
| `sp_complete_order` | 结算 | 状态校验 → 调 `fn_calc_fare` 按快照计价 → 改状态 → 写日志 |
| `sp_cancel_order` | 取消 | 状态守卫 → 改状态 → 写日志 → 关闭未应答邀请 |
| `sp_expire_dispatch` | 批量清理 | 把超时未应答的邀请置为 expired |

> **为什么把逻辑放进存储过程而不是应用层**：接单涉及「资格复检 + 条件抢占 +
> 撤销其他邀请 + 写状态日志」四步，必须是原子操作。放在数据库里可以保证
> **任何调用方（Web 界面、测试脚本、手工 SQL）都走同一条正确路径**，
> 不会因为某个调用方漏了一步而产生不一致数据。

### 6.3 两个实测踩到的坑

**(1) `GET DIAGNOSTICS` 不填充 handler 块内声明的变量**

最初的异常处理写成：

```sql
DECLARE EXIT HANDLER FOR SQLEXCEPTION
BEGIN
    DECLARE v_errno INT DEFAULT 0;          -- ← 声明在 handler 内部
    GET DIAGNOSTICS CONDITION 1 v_errno = MYSQL_ERRNO, ...
```

结果永远取到 `errno = 0`、消息为空。对照实验（`p_diag_inner` vs `p_diag_outer`）证实：

| 变量声明位置 | `GET DIAGNOSTICS` 结果 |
| --- | --- |
| handler 的 `BEGIN...END` 内 | `errno=0`，消息空 ❌ |
| 过程主体中 | `errno=1146`，消息正确 ✓ |

**修正**：把 `v_errno` / `v_errmsg` 声明到过程主体里。

**(2) 存储函数与触发器需要 SUPER 权限**

本机 `log_bin=1` 且 `log_bin_trust_function_creators=0`，
此时非 SUPER 账号创建存储函数/触发器会报 `ERROR 1418`。
`root` 有 SUPER，因此本项目的 DDL 一律用 root 执行。
生产环境更稳妥的做法是给应用账号授 `SUPER` 之外的
`log_bin_trust_function_creators=1`（需改 `my.ini` 并重启）。

## 七、触发器设计

全库**只有 1 个触发器**：`trg_review_after_insert`。

```sql
CREATE TRIGGER `trg_review_after_insert`
AFTER INSERT ON `order_review`
FOR EACH ROW
BEGIN
    UPDATE `driver` d
       SET d.`service_score` = (
               SELECT ROUND(AVG(r.`score`), 2)
                 FROM `order_review` r
                WHERE r.`driver_id` = NEW.`driver_id`
           ),
           d.`review_count` = (
               SELECT COUNT(*)
                 FROM `order_review` r
                WHERE r.`driver_id` = NEW.`driver_id`
           )
     WHERE d.`driver_id` = NEW.`driver_id`;
END
```

**在触发器里回读 `order_review` 求精确均值**，结果与 `ROUND(AVG(score), 2)` 完全相等。

> **纠正一个常见误解**：MySQL 只禁止触发器**修改**它所在的那张表
> （`ERROR 1442: Can't update table ... already used by statement`），
> **并不禁止读取**。本项目实测验证过：在 `AFTER INSERT` 触发器里 `SELECT` 本表，
> 新插入的行已经可见，因此求出的均值天然包含本次评价，无需特判。

**为什么不用增量公式**：曾经用过
`新均值 = (旧均值 × 旧评价数 + 本次评分) ÷ (旧评价数 + 1)`，
它每一步都要 `ROUND` 到 2 位小数，**误差会逐次累积**。
实测某司机 15 条评价，精确均值 4.2667，增量公式得到 4.25，
累积偏差 0.02，导致管理端的「服务分一致性校验」显示出「不一致」，
看起来像系统出了故障。改用回读求精确值后问题消失。

**性能权衡**：回读是 O(n)、增量是 O(1)。本场景每次评价只扫该司机的评价行
（几十条量级），代价可忽略；**正确性远比这点开销重要**。
若评价量真到百万级，可改回增量 + 定期重算校正。

**可验证性**：视图 `v_driver_service_score` 同时给出
「触发器维护值」与「实时聚合值」，管理员端页面直接对比两者是否一致 ——
这是对冗余设计正确性的证明。**实测 24 名有评价的司机全部严格相等**。

### 刻意没有用触发器的地方

**不用触发器写订单状态日志**。原因是触发器拿不到「谁操作的」这一上下文，
需要靠 `SET @app_account_id` 之类的会话变量传递，脆弱且难调试。
状态日志改由应用层在**同一事务内**显式写入，`operator_type` / `operator_id` 准确可靠。

## 八、事务与并发控制

### 8.1 必须包在事务里的操作

下单（快照+建单+日志）、接单、拒单、行程推进、完成结算、取消、派单批次生成、
计价规则版本切换。

### 8.2 两个司机同时抢同一订单

**方案：条件更新 + 判断影响行数，并把这一步放在最前面。**

```sql
START TRANSACTION;

-- 第 1 层（最先执行）：条件抢占
UPDATE `ride_order`
   SET `status` = 'accepted', `driver_id` = p_driver_id, `accepted_at` = NOW()
 WHERE `order_id` = p_order_id
   AND `status`   = 'pending';          -- ← 并发守卫
-- ROW_COUNT() = 1 → 抢到；= 0 → 已被别人接走，ROLLBACK

-- 第 2 层：资格复检 + 取可运营车辆（此时已无同单竞争者）
SELECT v.`vehicle_id` INTO v_vehicle_id
  FROM `driver` d JOIN `account` a JOIN `vehicle` v
 WHERE d.`driver_id` = p_driver_id AND ... AND v.`operate_status` = 1
 LIMIT 1 FOR UPDATE;

-- 第 3 层：回填车辆、更新邀请状态、写日志
COMMIT;
```

**为什么成立**：`UPDATE ... WHERE status='pending'` 会先对目标行加排他行锁；
并发事务二在此阻塞，待事务一提交后重新读取，发现 `status` 已不是 `pending`，
匹配 0 行而干净退出。**关键纪律：必须判断 `ROW_COUNT()`，
绝不能写成「先 SELECT 查状态，再无条件 UPDATE」。**

> ⚠️ **加锁顺序是这个方案的关键，而它是实测出来的。**
> 最初的实现把「FOR UPDATE 资格复检」放在 UPDATE 之前，
> 5 个司机并发实测**稳定触发死锁 `ERROR 1213`**：
> InnoDB 的 `LATEST DETECTED DEADLOCK` 报告显示事务持有 `driver` 表的行锁、
> 正在等待 `ride_order` 的行锁，各事务在两张表之间交叉持锁形成循环等待。
> 把条件 UPDATE 提到最前面后，竞争在第一步就被行锁串行化：
> 只有一个事务能继续往下走，其余事务在该处等待，
> 醒来时匹配 0 行而退出，**根本不会去申请 driver/vehicle 的锁**，死锁环无从形成。
> 修复后 4 个落败者全部干净返回 `ALREADY_TAKEN`，无一死锁。

### 8.3 三层防护汇总

| 层 | 机制 | 拦截什么 |
| --- | --- | --- |
| 1 | `WHERE status='pending'` + `ROW_COUNT()` | 两个司机同时抢单 |
| 2 | 事务内 `FOR UPDATE` 复检资格 | 接单瞬间司机下线/车辆停运 |
| 3 | 唯一索引 `uk_active_driver` | 一个司机同时接多单（兜底） |

第三层触发时由 `DECLARE EXIT HANDLER FOR 1062` 转换为业务语义的 `DRIVER_BUSY`，
而不是把原始的「唯一键冲突」错误抛给用户。

### 8.4 隔离级别

本机默认 `REPEATABLE-READ`。上述条件更新方案**不依赖隔离级别**——
它靠的是行锁与影响行数判定，即使在 READ COMMITTED 下同样正确。

## 九、设计取舍与已知局限

### 9.1 反规范化：为什么冗余状态时间戳列

`ride_order` 上有 6 个状态时间戳列，而 `ride_order_status_log` 已经记录了完整历史。
**这是有意的反规范化**：

- 只放时间戳列：读取快，但新增状态节点要 `ALTER TABLE`，且无法追溯「谁改的、改了几次」；
- 只放日志表：灵活可追溯，但每次显示当前状态都要连表取最后一条，列表页性能差；
- **双写**：时间戳列服务 UI（列表页直接 SELECT 出时间线），日志表服务审计与统计。
  这是「用反规范化换读性能 + 用事件溯源保审计」的典型组合。

### 9.2 已知局限

| 局限 | 影响 | 可行的改进方向 |
| --- | --- | --- |
| 订单状态用 `ENUM` | 新增状态需 `ALTER TABLE` | 状态经常扩展时改用 `VARCHAR` + 字典表 |
| 司机服务分用触发器维护的冗余列 | 与源数据可能漂移 | 已用视图提供一致性校验；可加定时任务定期重算 |
| `v_order_status_duration` 用条件聚合 | 大订单量下要全表聚合 | 可物化为汇总表，用定时事件增量更新 |
| 派单策略按「同区域 + 车型 + 服务分」 | 未考虑实际距离 | 可接入经纬度做球面距离排序 |
| 无分库分表 | 单库单表 | 订单量上亿时可按时间分区（`order_track` 尤其适合 RANGE 分区） |
| 会话存数据库 | 每次请求多一次查询 | 可加 Redis 缓存层（本作业不引入外部依赖） |

### 9.3 与需求文档的对应关系

| 需求编号 | 实现方式 |
| --- | --- |
| 核心1 乘客下单 | `sp_create_order` + `common_address` 复用 + `v_pricing_current` 取价 |
| 核心2 平台派单与司机接单 | `sp_dispatch_order` + `order_dispatch` 表 + 接单/拒单 |
| 核心3 司机行程执行 | `mark_arrived` / `mark_started` / `sp_complete_order` |
| 核心4 订单状态实时追踪 | 状态机 + 6 个时间戳列 + `ride_order_status_log` + `v_order_status_duration` |
| 核心5 订单计价 | `fn_calc_fare` + 价格快照列 |
| 核心6 司机与车辆管理 | `driver` / `vehicle` 表 + `v_available_drivers` + 三层资格防护 |
| 核心7 账号与角色管理 | `account` 泛化/特化模型 + `user_session` + 路由层角色校验 |
